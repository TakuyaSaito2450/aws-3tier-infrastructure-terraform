# 進め方（4週間）

このリポジトリは雛形です。**そのままGitHubに上げても評価されません。** 自分で1度 apply して壊して直した記録を残してはじめてポートフォリオになります。

## week 1 — 動かす

- [ ] AWSアカウントで `terraform apply` を通す
- [ ] ALB経由でページが表示され、リロードでInstance IDが変わることを確認
- [ ] `terraform destroy` で全リソースが消えることを確認
- [ ] 詰まった箇所をメモに残す（READMEの「苦労した点」の材料になります）

apply が一発で通ることはまずありません。**通らなかった記録こそが価値**なので、エラーメッセージと対処を残してください。

## week 2 — 壊して直す

- [ ] EC2を1台手動終了 → ASGが再作成することを確認
- [ ] nginxを止めて → ALBがunhealthy判定し、アラームメールが届くことを確認
- [ ] SGのingressをわざと消して → 疎通不可を再現し、原因特定の手順を記録
- [ ] `single_nat_gateway = false` に変更 → `terraform plan` の差分を読む

面接で聞かれるのは「作れますか」ではなく「壊れたとき何を見ますか」です。ここが答えられる材料になります。

## week 3 — 仕上げる

- [ ] 構成図を作図ツールで清書し、READMEに画像で貼る
- [ ] 「苦労した点」を2〜3件、事象/原因/対処の順で記述
- [ ] `terraform fmt -recursive` と `validate` を通す
- [ ] コミットを小さく分ける（1コミットで全部入りにしない）
- [ ] READMEの概算コストを実際の請求額で更新

## week 4 — 職務経歴書に載せる

- [ ] 職務経歴書の冒頭にGitHub URLを記載
- [ ] 「自己PR」にこのリポジトリへの言及を1文追加
- [ ] 応募開始（MSP系8社＋OCI系5社）

## コミットの分け方（例）

```
feat: network モジュール追加（VPC/3層サブネット）
feat: security モジュール追加（SG/IAMロール）
feat: compute モジュール追加（ALB/ASG）
feat: database モジュール追加（RDS）
feat: monitoring モジュール追加（アラーム/ダッシュボード）
docs: README に構成図と設計判断を追記
fix: ALB egress 未設定によるヘルスチェック失敗を修正
```

一括で1コミットにすると、実際に手を動かしたのか判断できません。**作業の順序が見えること**自体が信頼材料になります。

---

## 費用を抑えるコツ

- 作業する日だけ apply し、終わったら必ず destroy
- AWS Budgets で月3,000円のアラートを設定しておく
- `desired_capacity = 1` にすれば検証中のEC2費用は半分
- NAT Gatewayが最大の費用要素。不要なら `enable_nat_gateway = false`（SSM接続は使えなくなります）
